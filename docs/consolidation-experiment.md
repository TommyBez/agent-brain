# Autonomous consolidation experiment

This experiment evaluates content changes on local copies of an MCP snapshot. It does not change the production nightly Workflow, connect to the database, regenerate embeddings, export to GitHub, or write to MCP.

## Design

- Capture all canonical pages and their current versions through read-only MCP calls.
- Freeze an independent preservation inventory and source-backed questions before observing outputs.
- Start two independent copies from exactly the same snapshot.
- Run 20 sequential full-corpus passes in each arm. Every pass calls the proposal model; there is no unchanged-page checkpoint that could conceal churn.
- Arm A applies proposals passing deterministic checks. Arm B applies the same checks and additionally requires Jev approval.
- Keep the generator, prompt, operation schema, and Jev thresholds fixed for the complete run.
- Save each generation, evaluation, application decision, and resulting snapshot. Resume uses persisted proposals and evaluations, and rejects changed source data, code, or evaluation criteria.

The generator proposes at most one change per target page per pass. Evidence is validated against the immutable input to that pass; target versions are checked against the current copy. This batch rule is specific to the isolated simulation and must not be copied into a production writer with concurrent external edits.

## Allowed transformations

The proposal engine supports deduplicating or consolidating a passage, resolving an already answered question, refreshing a summary, and adding a supported typed link. Each proposal cites exact passages from identified source versions. It cannot create or delete pages, and it preserves surrounding content and page metadata.

The prompt forbids new human tasks, invented questions, maintenance diaries, claims of external verification, and stylistic rewriting without a knowledge benefit. Existing factual uncertainty and historical decisions must survive unless the supplied evidence resolves them. A no-op is a valid outcome.

Deterministic checks enforce exact matches, versions, known link targets, source references, and some recognizable new questions or requests. They do not establish semantic truth; preservation and usefulness require independent assessment.

The first volume experiment exposed a concrete preservation failure: shortening a source line removed later source dates while retaining a fact first documented on the later date. Absolute URLs and wiki references are checked, but ordinary relative Markdown links and the association between each fact, date, and attribution are not fully protected. Also, each new pass treats the current copy as evidence; an accepted distortion can become its next input. The original snapshot is retained for independent assessment, not enforced as immutable claim provenance by the writer. These experimental modules are not suitable for production writes without addressing these limitations.

## Jev

Jev is called through the public AI SDK `experimental_evaluate` API and `createGateway().evaluationModel("typesafe-ai/jev")`. The adapter returns only raw probabilities, model and allowlisted usage. Each probability refers to that question's `true` class; the adapter does not decide acceptance. In the historical positive-question experiments, `applyPositiveConsolidationPolicy` explicitly applies thresholds 0.9, 0.9, 0.9, and 0.8 for factual support, preservation, absence of new human action, and meaningful improvement respectively. These are explicit experimental settings, not measured calibration guarantees. The judgments can overlap and are not statistically independent.

The 2026-09-19 SDK migration removed the adapter's legacy `allowed` and `reasons` fields, which previously used positive polarity even when supplied defect questions. Defect experiments already routed from raw probabilities and did not use those fields. The SDK owns the wire protocol; retries are disabled in the SDK because experiment runners own attempts and journals. Warning-bearing responses are rejected before SDK logging, and errors retain only sanitized diagnostic fields. New run protocols hash the package manifest and lockfile as well as the local evaluator source. Historical receipts are preserved; resuming them with changed source or dependency hashes remains forbidden. The source snapshot for this migration is in `artifacts/consolidation/2026-09-19-jev-sdk-migration/before/`, with TypeScript snapshots suffixed `.ts.txt` to exclude them from compilation.

Jev receives content before/after and the complete cited source pages. Changing embedding timestamps or version counters is excluded from its content assessment. Malformed Jev responses and provider errors interrupt the run rather than count as qualitative rejections.

Generator output is checked independently: malformed individual proposals are recorded and rejected, while valid siblings remain eligible. A truncated or malformed complete generation produces a recorded `generationFault` and no content changes for that pass. Usage is retained, and the fault must not be counted as successful semantic convergence. Only final completion text is retained for diagnosis; reasoning content is excluded.

## Run

Private snapshots, criteria, outputs and reports belong under the Git-ignored `artifacts/consolidation/` directory. `AI_GATEWAY_API_KEY` is loaded with `@next/env`; never include credentials in artifacts. Running this command sends snapshot content to Vercel AI Gateway and the selected model providers and incurs API charges.

```sh
node --import tsx scripts/evaluate-consolidation.ts \
  --snapshot artifacts/consolidation/<experiment>/initial.json \
  --output artifacts/consolidation/<experiment> \
  --passes 20 --arm both
```

The output directory must already contain `evaluation-spec.json`. The snapshot format is `{ "capturedAt": "...", "pages": [...] }` with complete `BrainPage` objects. The input corpus is bounded at 100,000 serialized characters and is never silently truncated.

## Assessment

Inspect snapshots 1, 5, 10 and 20 against the initial snapshot and frozen criteria. Count preserved, partial, lost and altered facts separately. Compare source-backed answerability, metadata and relations, new human requests, unsupported claims, useful changes, rejected useful changes, reversals and repeated proposals. Record both accepted-write convergence and proposal convergence: a gate can stop writes while the generator keeps proposing the same rejected work.

For the initial four-page corpus, this is one stochastic trajectory per arm. It measures stability and observed content quality on those pages; it does not establish general model superiority, population-level error rates, or production retrieval, concurrency, indexing and Workflow correctness. The generator's token counts support an estimated cost, while Jev also returns recorded Gateway billing metadata. Successful-call totals exclude synthetic preflight calls and any provider attempts without usage receipts.

The completed 2026-09-17 comparison ran all 20 passes per arm. A applied eight changes and reduced Markdown by 29.52%, but altered one source-date attribution. B rejected all 38 evaluated proposals and preserved the original corpus, including maintenance noise. Each arm also recorded one unusable generation. Independent agent assessment found useful changes among the rejected proposals; a separate Jev diagnostic rejected the flawed A change. Neither configuration was connected to the production nightly writer. Detailed private receipts and the report are in the ignored experiment artifacts.

Sources: [Vercel evaluation models](https://vercel.com/docs/ai-gateway/modalities/evaluation), [Jev announcement](https://vercel.com/changelog/typesafe-ai-jev-now-available-on-ai-gateway).

## Paired blind assistant judgments

`scripts/evaluate-consolidation-paired.ts` repeats 20 sequential Jev-gated passes from the same initial snapshot. Before calling Jev for a pass, it writes `blind-request-NN.json` and exits with `awaiting_review`. The root assistant reads those candidate inputs and records `pass`, `fail` or `uncertain` plus a concrete rationale for each of the same four criteria in `assistant-review-NN.json`. It also assigns a family identifier to keep superficial variants together during analysis.

On the next invocation, the runner validates and freezes the complete review before any Jev request. All four assistant criteria must pass for the counterfactual `assistantWouldPass` result. Only the unchanged Jev thresholds determine applied changes; neither the assistant's labels nor rejection feedback reach the generator. New Jev scores stay out of console output and are inspected only after the run completes. Saved generations and evaluations are reused on resume, while changes to frozen inputs or reviews stop the experiment.

The frozen experiment specification defines family-based exploratory/heldout assignment and threshold sensitivity analysis. Agreement with the assistant is a reference judgment, not objective ground truth. Missing negative examples, very few families and uncertain labels limit calibration; the analysis must report these limits and never update acceptance thresholds automatically. Private snapshots, reviews and receipts remain under the ignored artifacts directory.

The completed paired run on 2026-09-17 generated 40 proposals over all 20 passes. Two failed exact-quotation validation before semantic assessment. Of the remaining 38, the assistant would approve 31, reject six, and leave one uncertain; Jev rejected all 38. The final snapshot is identical to the initial snapshot. All review hashes, candidate inputs and review-before-evaluation timestamps were verified.

At the original preservation threshold, Jev passed only two of the 31 proposals the assistant labeled positively on that criterion. Scores overlapped between positive and negative reference labels. The predefined sensitivity vector `0.85 / 0.70 / 0.90 / 0.60` would admit nine assistant-positive proposals and one uncertain proposal; `0.80 / 0.60 / 0.90 / 0.50` would admit 21 positives, one negative and one uncertain. These are counterfactual classifications of the observed proposals, not simulations of the resulting changed trajectory.

There were only two overlapping-edit families, both assigned to exploration by the frozen partition rule, leaving no heldout family. No proposal introduced a human task, so that criterion had no negative reference examples. No threshold vector was validated or promoted. Jev's recorded cost was $0.007566804; generator usage supports an estimated $0.2442228, excluding Codex review and analysis.

The assistant's preservation rubric explicitly allows cross-page deduplication when an identifiable, linked source survives; Jev's unchanged question does not state that case as explicitly. Aligning that wording is a candidate follow-up, not a proven explanation for score differences. In addition, cited pages remain frozen at pass start: mutually dependent proposals need a check of the combined result before this design can support production writes.

`scripts/analyze-consolidation-paired.ts --input <directory>` analyzes a completed run locally, verifies frozen reviews and evaluations, and writes `analysis.json` and `analysis.md` without provider calls. The private paired-run report includes each proposal's four original judgments and Jev scores.

## Shared-rubric replay with an independent subagent

The next experiment reuses the 38 validated candidate inputs without regenerating proposals. A new subagent, created without conversation history, reads only a separate packet containing randomly ordered opaque case IDs, the before/after/evidence/operation inputs, and the exact revised rubric. Previous scores, reference judgments, source mappings and reports are not included. This reduces exposure to prior results but does not eliminate model biases; access isolation is an instruction boundary, not a separate filesystem permission boundary.

`lib/maintenance/consolidation-rubric.ts` defines the revised four questions. The review packet's `rubric.json` is checked against that definition before any evaluation. The subagent assigns pass/fail/uncertain and evidence-grounded reasons to every case; its complete output is hashed and frozen before provider calls. Root does not adjust the reference labels. The prior root labels are only a secondary consistency comparison.

`scripts/evaluate-jev-rubric-replay.ts --input <directory>` compares the unchanged baseline questions with the revised questions, holding thresholds at 0.9/0.9/0.9/0.8. It alternates variant order and evaluates each case three times per variant, for 228 evaluations. It persists successful receipts, attempt metadata, code and input hashes, costs and comparison summaries. Repeated calls measure observed API stability, not independent examples or a guarantee of independent provider execution. No new thresholds or corpus edits are applied.

The revised wording makes cross-page preservation and superseded maintenance notes explicit. It may affect borderline policy interpretations, so greater agreement means closer agreement with this revised reference rubric, not proven superiority on an independent test set. This replay is development evidence. New families and a separately held-out validation set are required before promoting a calibrated configuration, followed by a sequential corpus experiment that checks combined changes across pages.

The completed replay used a fresh GPT-6 Astra subagent with inherited ultra reasoning and no conversation history. It approved 22 cases and rejected 16 under the shared rubric; these labels were frozen without root edits. Both question variants rejected every case in all three repetitions. On preservation, baseline accepted two of the 22 reference positives each time, while revised accepted none; on usefulness the counts were four each time versus zero, zero and one. Neither version was promoted, and no thresholds changed.

All 228 successful receipts were locally reverified without additional provider requests. They record $0.046521216 in known Gateway cost; ten HTTP 529 responses required retries, for 238 attempts in total. Charges for unsuccessful attempts are not established by successful-call receipts. The private report retains all four subagent judgments, reasons and score distributions for each case. The comparison with the earlier root labels remains secondary because both reviewer context and explicit rubric differ.

## Controlled pairs with family-heldout validation

The next experiment uses entirely fictional Italian documents in twelve different knowledge families. Each family supplies one intended useful consolidation and four controlled variants: unsupported attribution or assertion, omission of unique useful knowledge, a new human request, and cosmetic title change. A single mutation may fail several overlapping criteria. Design intent is metadata, never a replacement for the independent reference labels.

`scripts/prepare-jev-controlled.ts --output <new directory>` checks the fixture's exact citations, historical target, unique family/source identities and five variants per family. It randomly assigns eight whole families to calibration and four to validation, shuffles all sixty cases under opaque identifiers, and creates a separate reviewer packet. It freezes the V2 rubric, analysis rule and design code hashes. Sources are disjoint across families, but broad task types and construction conventions are shared; this is a synthetic development benchmark, not a representative production sample.

A fresh subagent without inherited conversation reads only the packet's complete inputs, rubric and instructions. It receives neither intended variants, partition, prior judgments nor Jev scores. Its pass/fail/uncertain judgments for all four criteria are copied without root edits and frozen before any Jev calls. Instruction-based context isolation does not eliminate shared-model biases or establish objective ground truth.

`scripts/evaluate-jev-controlled.ts --input <directory> --phase calibration` evaluates only the forty calibration cases, three times each, using the shared V2 rubric. `scripts/analyze-jev-controlled.ts --input <directory> --phase calibration` verifies the frozen inputs and receipts without network calls, then selects one exploratory threshold per criterion from the grid 0.00–1.00 in steps of 0.01. It selects the lowest threshold that accepts no reference-negative case in any calibration repeat; missing negative coverage or no qualifying threshold is marked infeasible. Uncertain labels do not fit thresholds. An overall fail takes precedence over uncertainty.

The predeclared feasibility screen requires at least six distinct positive and six distinct negative calibration cases per criterion, zero negative passes in any repeat, and at least half the positive cases passing all three repeats. The combined gate must also preserve at least half the overall positives across all repeats and pass no negatives. This is a development screen, not a statistical guarantee or deployment criterion.

The validation phase requires a complete, receipt-verified calibration phase and the immutable selection. It verifies the selection's source, rule, hash and chronology and recomputes it from calibration scores before sending any validation input. It then evaluates the twenty heldout cases three times, without refitting. Validation is diagnostic even if calibration fails its feasibility screen; the failure remains visible. Summaries report per-repeat decisions, criterion AUC using per-case medians, designed-pair ordering, excluded pairs whose blind labels contradict their intended direction, instability, and successful-receipt costs. Repetitions are not independent cases and median scores do not replace per-call decisions.

Both phases retain sanitized attempt journals and hashed resumable receipts, reject unknown interrupted attempts, and support `verifyOnly` with no additional provider calls. This experiment has no database client, generator or production write path. No threshold or rubric is promoted automatically; combined-edit consistency and a later sequential test on the real corpus remain necessary before live consolidation.

The completed controlled test on 2026-09-17 produced 180 successful evaluations, costing $0.028592172 in recorded Jev usage. The blind subagent labeled ten proposals pass, 48 fail and two uncertain. Calibration contained seven overall positives, 32 negatives and one uncertain; validation contained three positives, 16 negatives and one uncertain. The two uncertain intended-good cases concern omitted project context and remain unchanged in the reference.

All 44 eligible designed pairs ranked in the expected direction in every repeat: 12/12 for support, 10/10 for preservation, 12/12 for human action and 10/10 for usefulness. Four criterion-pairs were excluded because the intended-good reference was uncertain. These paired comparisons share twelve families and do not establish independent population-level accuracy.

The frozen threshold rule selected 0.39 / 0.61 / 0.08 / 0.89. It failed the predefined feasibility screen already in calibration: the combined gate accepted three of seven positives, then zero of three heldout positives, with zero overall negative approvals in both groups. Usefulness was the bottleneck: at 0.89 it accepted four of 14 criterion-positive calibration cases and none of six heldout positives. The minimum selected human-action threshold also incorrectly passed one of four heldout negative cases at that criterion, although other criteria blocked final acceptance. By contrast, the original human-action threshold 0.90 rejected all twelve new human requests and accepted 45 of 48 no-new-request cases in every repeat. No configuration was promoted or refitted on validation.

The first sandboxed attempt encountered three transport failures without HTTP responses, and a credential-free connectivity check confirmed DNS failure. Its original protocol and journals remain untouched; a fresh network-enabled execution used identical inputs, labels and scoring code and completed all 180 calls without retries. Receipt/code/artifact hashes and selection chronology were reverified offline, and a separate subagent independently recalculated the reported result matrices. Synthetic pair discrimination is useful evidence, but the attempted global acceptance rule remains unsuitable for the intended autonomous consolidation.

## Jev with selective Kimi K3 review

The cascade experiment retains all four Jev criteria. Each criterion has a lower rejection boundary and an upper acceptance boundary. Scores below the lower boundary reject; scores at or above the upper boundary pass; intermediate scores require Kimi review. Any red criterion rejects the proposal immediately. Otherwise one Kimi call judges all gray criteria, using the complete before/after/source context and the complete V2 rubric, but receiving no Jev scores, boundaries, reference labels or prior evaluator responses. Kimi's verdict replaces the delegated criterion rather than being averaged with Jev. All four criteria must pass to approve; uncertainty or provider failure never approves a change or creates a human task.

`scripts/prepare-consolidation-cascade.ts` derives and freezes boundaries from the three revised-rubric repetitions of 98 previously observed proposals: 38 real candidates and all 60 cases from the earlier synthetic experiment. Both partitions of that earlier experiment are now development data. The rule uses the minimum positive score and maximum negative score, with an outward 0.05 margin and cent rounding. Uncertain references constrain both ends. When classes are separated, the two endpoints are ordered to preserve an intermediate review interval; overlapping classes produce a wider interval. Missing class coverage disables automatic decisions. These boundaries are conservative heuristics, not calibrated probability or accuracy guarantees.

After boundaries are frozen, the preparation script builds 48 new fictional proposals across eight source-disjoint families, six correlated variants per family. It shuffles opaque case IDs and creates a separate packet for a fresh reference subagent without conversation history. The reference assigns all four judgments before provider calls, without intended variant labels or thresholds; root preserves the result without relabeling. A separate audit compares every new source ID and exact Markdown hash against both historical development input sets. Distinct source identities do not establish a representative production distribution or eliminate shared construction conventions.

`scripts/evaluate-consolidation-cascade.ts --input <directory> --stage jev` performs one V2 evaluation per new case. The `--stage kimi` phase then evaluates every case independently with `moonshotai/kimi-k3` at high reasoning effort and structured JSON output. It also makes a separate selective call for each gray-routed proposal, alternating baseline/selective order across cases and using at most three case workers. Even when all four criteria are gray, the selective response is not reused for the complete baseline. The compared arms are original-threshold Jev alone, Kimi alone, and the frozen Jev–Kimi cascade. The complete Kimi baseline also audits proposals and individual criteria that Jev decides automatically.

Inputs, reference judgments, bands, development data, selection method, code and provider settings are hashed and checked before execution and resume. Each logical job permits at most three attempts, retrying only explicit HTTP 429 or 5xx responses. Transport failures with unknown outcomes are retained rather than blindly repeated. Failed receipts and unfinished attempt journals remain visible. `verifyOnly` validates completed stages without provider calls. The experiment has no production database write path.

`scripts/analyze-consolidation-cascade.ts --input <directory>` verifies the final run before writing an immutable report. It reports proposal and criterion errors against the blind reference, family-level recovery, automatic-decision disagreements, and the difference between intended mutations and actual reference labels. Gray criteria skipped after an automatic red are counted as not evaluated, separately from actual uncertain judgments. Recorded request costs, cache usage and summed request durations are retained; summed durations are not elapsed wall time. The experiment's total is Jev plus complete Kimi plus selective Kimi, while the operational cascade comparison is Jev plus selective Kimi versus complete Kimi alone. These arm totals overlap and must not be added. Cache effects shared within this batch limit extrapolation of the observed cost difference to isolated production runs.

The completed cascade experiment on 2026-09-17 used the frozen bands `0.00–0.98 / 0.15–0.82 / 0.13–0.76 / 0.26–0.93`. The independent reference labeled 16 proposals valid and 32 invalid. Original-threshold Jev accepted none; Kimi alone and the cascade each accepted 15 of the 16 valid proposals, with zero overall invalid approvals. Different valid cases were blocked by technical errors in the two Kimi arms: the full baseline had four unusable responses (one valid, three invalid cases), and selective review had two (one valid, one invalid). No valid proposal received an explicit semantic rejection from either complete gate.

Jev automatically rejected 18 reference-negative proposals and automatically accepted none, leaving 30 selective Kimi calls against 48 complete baseline calls, a 37.5% reduction. Valid proposals were recovered in all eight families. Agreement of whole-proposal decisions does not establish criterion-level reliability: preservation still had eight false passes in the baseline and two in the cascade, over different evaluated subsets. Other criteria prevented those errors from producing invalid overall approvals. Missing baseline responses are technical errors, not semantic disagreements with automatic decisions.

The final run contains 126 jobs with no retries: 48 Jev, 48 complete Kimi, and 30 selective Kimi. Its recorded cost is $2.170702176, with six failed-response charges unknown. Recorded operational subtotals are $1.3414944 for Kimi alone and $0.829207776 for the cascade; these incomplete subtotals do not establish an exact cost saving. Before this run, a floating-point summation-order bug blocked resume after 48 successful Jev calls and before any Kimi call. Those artifacts and the original runner source were preserved; only deterministic aggregation was corrected, and the identical cases, reference and bands were rerun in `stable-summary`. Including that $0.008627976 attempt and the $0.0097806 preflight gives $2.189110752 in known charges before separate format diagnostics. A second subagent independently reconstructed all final matrices and costs from receipts.

`scripts/diagnose-kimi-cascade-response.ts --input <completed directory> --limit 3` is a separate technical investigation. It verifies the completed benchmark, selects at most three failed Kimi jobs by immutable ID, freezes its specification, and makes one new call per job without retries or replacing benchmark results. It records only sanitized response structure and usage, excluding generated judgments and reasoning. All three diagnostic requests returned usable responses with unchanged inputs and settings, so the original failure cause was not reproduced. The original error records are too coarse to distinguish which response-format check failed. Recording specific safe validation reasons and usage even for unusable responses is necessary before the next sequential corpus test; the diagnostic successes do not repair the frozen quality result. No production gate or threshold was promoted.

Those three diagnostic calls cost $0.0835278, bringing the known total for all attempts and checks to $2.272638552 plus the six unknown failed-response charges. Detailed receipts, the final report, independent audit, and technical diagnosis remain in the ignored cascade experiment's `stable-summary` directory.

## Question polarity and threshold-position experiment

The next experiment compares three Jev formulations on identical inputs: unchanged V2 positive questions, literal negations with the exact true/false class definitions exchanged, and concrete defect-search questions retaining those exchanged class definitions. `lib/maintenance/consolidation-defect-questions.ts` defines these experimental arms. All answers are normalized to defect risk: one minus the positive answer, or the negative/defect answer itself, rounded to twelve decimal places. Raw answers are retained. The adapter's former positive `allowed` and `reasons` fields did not influence this experiment and have since been removed.

All 146 previously evaluated proposals, including earlier holdouts, are development data: 38 real proposals and 108 fictional controlled examples across 22 families. A separate blind subagent, without conversation history or model scores, labels 36 new fictional examples across six source-disjoint families under the exact V2 reference rubric. Its 144 criterion judgments are copied without root edits. The full reference, question texts, input documents, source-separation audit, code and selection method are frozen before Jev calls. Constructed source separation does not make the examples representative of production, and three repeats do not create three independent examples.

`scripts/prepare-jev-defects.ts` creates the packet and freezes the completed reference. `scripts/evaluate-jev-defects.ts` evaluates each case three times in all three arms, rotating question order and using at most three concurrent case workers. Calibration completes before threshold selection; validation can begin only after the runner independently recomputes and freezes all selected thresholds. Receipts, attempt journals, usage and code hashes support restart without repeating an unknown transport outcome. Only explicit HTTP 429 or 5xx failures permit bounded retries. Technical failures remain separate from semantic judgments; incomplete calibration blocks selection.

`lib/maintenance/defect-threshold-method.ts` defines the frozen selection rule. On a 0.01 grid from zero through 1.01, a single threshold either prioritizes zero missed defects or zero false alarms in calibration. The two-boundary rule allows a criterion below L, rejects at or above U, and otherwise delegates it. It maximizes automatic decisions subject to zero reference-negative automatic approvals, zero reference-positive automatic rejections and every uncertain reference remaining delegated in all repeats. Ties prefer the widest gray interval, then lower L and higher U. Missing class coverage disables automatic decisions. These empirical constraints are not a future accuracy guarantee, and per-criterion optimization is not whole-process optimization.

`scripts/analyze-jev-defects.ts` reports class distributions, repeat ranges, overlap, score distance to boundaries, crossings, matched question-arm differences and segmentation by source and family. It simulates every single grid threshold and one-boundary shifts of ±0.01, ±0.05 and ±0.10, including their effect on whole-proposal routing. Validation sweeps are retrospective scenarios, never newly validated settings. Kimi routing counts are simulated; this experiment makes no Kimi calls and does not infer its decisions or cost. No production threshold or document is changed.

The completed polarity experiment recorded 1,638 successful evaluations, no retries or technical errors, and $0.296275140 in reported Gateway cost. An independent Python reconstruction confirmed all twelve selected bands and their grid optima, then matched 800 result checks and 3,648 threshold/sensitivity checks without divergence. The browser simulator was checked at conversational and mobile widths, including changes of sample, question arm and threshold.

On the 36 new proposals, automatic criterion decisions for positive/literal-negative/defect-search questions were respectively: support 18.5%/40.7%/51.9%, preservation 22.2%/38.9%/40.7%, human action 97.2%/100%/94.4%, and utility 37.0%/24.1%/28.7%. No frozen automatic decision disagreed with the independent reference in validation. All twelve wholly valid proposals nevertheless required stronger review in every repetition and arm; the whole-proposal simulated Kimi counts averaged 16, 16.67 and 17 per pass. Better criterion-level automation therefore did not reduce whole-proposal calls on this holdout.

Support exposes a large real/synthetic difference in development: at risk threshold 0.50 every arm missed all fifteen reference-negative real proposals in every repetition, while detecting all twenty-five synthetic support defects. Those real proposals share only two families and include subtle attribution/date issues, limiting any broad generalization. Raising the defect-search support acceptance boundary from 0.12 to 0.17 looks harmless on new fictional validation but automatically passes twelve defective criterion observations across five real development cases. No such threshold change was promoted.

Utility remains strongly overlapping: under defect-search wording, valid criterion scores range from 0.09 to 0.46 and defective scores from 0.11 to 0.95 in validation. Raising its acceptance boundary from 0.09 to 0.14 reduces simulated Kimi calls from 51 to 46 over the three passes and automatically approves five valid proposal observations. It also incorrectly passes utility seven times across three defective validation cases, and sixteen times across six development cases. Other criteria prevent invalid whole-proposal approvals; that masking does not establish utility reliability.

The selection objective itself matters. It forbids disagreement on a positive criterion even inside a proposal that is negative on another criterion. One older synthetic case, S-C50, correctly deduplicates a tariff document but adds a request to consult the municipality. Its reference fails only human action; Jev assigns high support and preservation risk too. Protecting those reference-positive criteria expands their gray bands even though the proposal would already be rejected for human action. Whole-process optimization could handle this differently, but must still report hidden criterion errors and be frozen before a new validation set. This experiment does not choose a mixed-arm winner retrospectively or enable production writes.

## Source-support binary versus Choice comparison

`scripts/evaluate-source-choice.ts` runs a controlled component comparison on the approved 24-case dataset. Each case receives two fresh, single-question Jev calls: the existing defect question and a Choice question with `supported`, `contradicted`, and `unsupported`. The latter gives contradiction priority when several defects coexist. Its routing value is the returned probability mass of `contradicted` plus `unsupported`, without normalization or reconstructed confidence. A missing distribution or aggregate outside [0,1] is a technical error. The source bands remain 0.12/0.94, and the other three Jev scores are frozen from `run-defect-sdk-v2` in both arms. Kimi settings, input projection and routing remain unchanged. Identical Kimi requests share a fresh receipt.

The completed run is `artifacts/consolidation/jev-kimi-fixed-v1/run-source-choice-v1`. Its frozen protocol precedes all 48 Jev and 11 physical Kimi calls. Both arms produce 23 correct final decisions, one uncertain case and no false acceptance, false rejection or technical error. Binary requires ten Kimi calls; Choice requires eleven. On the 14 explicitly labeled source criteria, binary automatically passes eight valid cases and rejects three invalid cases; Choice passes seven and rejects four. Both defer three and make no incorrect automatic source decision. Choice resolves the source criterion of Q04, but another criterion already rejects that proposal. It unnecessarily delegates valid Q24, accounting for the extra Kimi call. Q02 remains uncertain in both arms. No threshold was refitted or production policy changed.

Gateway reports zero billed cost for Jev in this run, separate from its nonzero market-cost metadata. The physical experiment's reported cost is $0.1725384. Kimi receipts shared across arms must not be billed twice in that total. These are development results on six correlated scenarios with one measurement per arm, not population accuracy or evidence against every possible Choice policy.

The original runner and artifacts remain frozen. Its byte-for-byte replay check exposed an order-dependent floating-point sum in the physical cost total ($0.17253840000000004 versus $0.1725384); this does not change any model response or decision. The independent offline reconstruction in the run directory verifies receipts and semantics with decimal cost accounting, documenting the formatting discrepancy without rewriting original evidence or making additional provider calls.

## Kimi source-support verdict clarification

`scripts/evaluate-kimi-source-contract.ts` compares the unchanged Kimi instructions with an experimental source-only clarification from `lib/maintenance/kimi-source-contract.ts`. The existing adapter is preserved. The added instruction requires `fail` for an added fact unsupported by the supplied material even when it might be true externally; `uncertain` is reserved for genuine interpretive ambiguity. Faithful paraphrases and direct implications remain acceptable, and unchanged claims need not be established again. Other criteria, input projection, model settings and response schema are unchanged.

The pre-registered run at `artifacts/consolidation/jev-kimi-fixed-v1/run-kimi-source-contract-v1` made 52 successful calls: both instruction variants on 14 existing source-labeled cases and 12 new cases from six contrast pairs. The new fixture and candidate prompt were prepared separately and independently reviewed before calls. Actual three-criterion selections were preserved for Q02 and Q21; the remaining 24 inputs were source-only diagnostic evaluations. Baseline achieved 25/26 correct source verdicts with one uncertain; clarified achieved 26/26, including 14/14 valid rewrites and 12/12 unsupported or contradicted changes. Both got all 12 new cases correct. The observed gain is Q02, not a measured improvement across the new families. No false pass, false rejection or technical error occurred. Reported cost was $0.6327684.
